## Objective
A community created by the Manager wizard gives its deployer real governance voting power before authority is finalized: 1 membership token (1e18 units) minted to the deployer and self-delegated, shown to the admin before signing, proven by verification, and never minted twice on resume.

## Problem
The wizard creates a community whose membership token has zero supply, so nobody can propose, vote or reach quorum (evidence in the issue: Base Sepolia community 7, `totalSupply() = 0`, `getVotes(deployer) = 0`). Two things are missing: a mint, and `delegate(self)`, because the token is `ERC20Votes` and voting power only counts after delegation.

## Decisions (resolved from code evidence)
- **D1 Amount = exactly 1 token (`parseEther("1")`, 1e18 units), a fixed constant, not a new form field.** 1 token is the minimum the owner accepts; threshold is 0 and quorum is 4% so any positive amount works; 1e18 is far below `MAX_SUPPLY` on a zero-supply token. A fixed constant keeps the slice small and the config/session shape unchanged; the amount is shown in the new step's name/purpose, the tx label and the review step. (If the owner later wants it configurable, that is a separate Improvement.)
- **D2 Minter role holder = the deployer wallet, granted just-in-time, in both modes.** The deployer holds ADMIN in both modes until FINALIZE, so it can `grantRole(11, deployer, 0)` itself; no coordinator or contract change. After minting it calls `renounceRole(11, deployer)` so the deployer does not keep a permanent mint power the staged lifecycle did not give it (matters most in governance-managed mode, where the deployer ends with no admin; admin-managed keeps ADMIN anyway but still should not keep an extra standing minter role). Result: only Engagements holds role 11 after the run, exactly as today.
- **D3 Ordering = a new step `INITIAL_VOTING_POWER` between `CONFIGURE_ACCESS_PERMISSIONS` and `FINALIZE_AUTHORITY_MODE`.** It runs before ADMIN moves, so the staged authority lifecycle is untouched in both modes. It is a separate step rather than extra txs in CONFIGURE so (a) the admin sees a labelled row with the amount before signing (transparency goal of SHI-147), (b) a failure here does not replay CONFIGURE, and (c) resume granularity is per step. Transaction count: 4 (`grantRole` minter, `mint`, `delegate`, `renounceRole`); fewer when resuming (see S4).
- **D4 Idempotency from chain state, not session state.** Each tx is guarded by a read so a re-run after a partial failure sends only what is missing: `hasRole(11, deployer)` before grant/renounce, `balanceOf(deployer) >= amount` before mint, `delegates(deployer) == deployer` before delegate. A second full run therefore mints nothing.
- **D5 Old sessions need no migration** (incompatible step list ⇒ restart, `useDeployWizard.ts:74-79`). Existing communities (e.g. community 7) are out of scope (see Non-goals).

## Specs
- **S1 (new step contract)**: `StepKey` gains `INITIAL_VOTING_POWER`; `WIZARD_STEP_ORDER` is `PRECHECKS, DEPLOY_STACK, CONFIGURE_ACCESS_PERMISSIONS, INITIAL_VOTING_POWER, FINALIZE_AUTHORITY_MODE, VERIFY_DEPLOYMENT`; `STEP_META.INITIAL_VOTING_POWER` has `expectedTxCount: 4` and a name/purpose that states the amount ("1 membership token") and that the wallet signs a temporary minter grant, the mint, the self-delegation and the grant renounce. A session persisted with the old step list is rejected by the existing compatibility check and restarts.
- **S2 (execution)**: Executing `INITIAL_VOTING_POWER` sends, in order, only from the connected deployer wallet and only with the compiled `MembershipTokenERC20Votes` ABI + `ShiftAccessManager` ABI: `grantRole(11, deployer, 0)` on the run AccessManager; `mint(deployer, 1e18, <reason>)` on the run membership token; `delegate(deployer)` on the token; `renounceRole(11, deployer)`. It runs after CONFIGURE and strictly before FINALIZE (step order, S1), in both authority modes, never reading mode to change behavior.
- **S3 (fail closed)**: The step throws with a specific message and sends nothing further when: the run membership token or AccessManager address is missing/stale; the deployer lacks ADMIN when it needs to grant the minter role; the post-state is wrong (after the step `balanceOf(deployer) < 1e18`, `delegates(deployer) != deployer`, or deployer still holds role 11). It never grants role 11 to any account other than the deployer.
- **S4 (resume idempotency)**: Running the step again after any partial or full completion mints at most once in total: skipped txs are decided by chain reads (D4). Resume with `balanceOf(deployer) >= 1e18` sends no mint; with `delegates(deployer) == deployer` sends no delegate; with the role already renounced sends no grant/renounce; fully complete sends 0 txs.
- **S5 (display before signing)**: The step list shows the new step with its name, purpose (amount stated) and per-tx labels in es and en (grant minter role, mint 1 token, self-delegate, renounce minter role), `expectedTxCount` is included in the displayed count, and the mock executor emits `expectedTxCount` hashes for it.
- **S6 (verification)**: `VERIFY_DEPLOYMENT` adds two checks: `INITIAL_VOTES_DEPLOYER` — `getVotes(deployer) >= 1e18` (the amount the wizard showed; `>=` so later Engagements mints cannot fail a re-verify) and `delegates(deployer) == deployer`; `ROLE_MEMBERSHIP_MINTER_DEPLOYER_REVOKED` — deployer does NOT hold role 11. Unreadable values fail the check with an explicit reason (same pattern as `authorityCheck`). Failing either blocks completion via `allVerificationChecksPassed`. Existing 17 + 3 mode checks are unchanged.
- **S7 (ABI guard)**: `MembershipTokenERC20Votes` is exported from `compiled-abis.ts` and used for mint/delegate/reads; the compiled-ABI guard test passes unchanged and an executor test decodes the sent calldata with the compiled ABI/selectors.
- **S8 (docs)**: `.github/project-management/STATUS_REVIEW.md` and `IMPLEMENTATION_STATUS.md` (wizard step list, expected tx counts) record the new step; `docs/EN` wizard-flow mentions are reconciled where they list the steps.
