## Objective

Make engagement submission and lifecycle inspection in Manager truthful and usable for Base Sepolia validation: what the list/detail show must match what the indexer actually projects and what the contracts actually emit, and chain-confirmed vs indexer-confirmed state must be signalled honestly (including `lagging`).

## Problem (verified, not assumed)

1. **Manager GraphQL queries target entities that do not exist.** `EngagementsQuery` selects `claimss(...)` with field `claimant` (`apps/web/lib/graphql/queries.ts:440,446`) and `EngagementQuery` selects `claims(id: $id)` with `$id: Int!` and a nested `jurorAssignments` (`queries.ts:487-503`). The generated indexer schema only has `engagements(id: String!)` / `engagementss(...)` with `participant` and no relation field (`apps/indexer/generated/schema.graphql:36-37,816-826`); jurors live in separate `jurorAssignmentss` (`schema.graphql:40-41,1084-1090`). The indexer ids are `"<communityId>:<engagementId>"` text (`apps/indexer/src/index.ts:386`). The unit test pins the wrong aliases (`apps/web/lib/graphql/queries.test.ts:17-20`) and MSW fixtures return the legacy shape (`apps/web/tests/unit/mocks/handlers.ts:110-125`, `fixtures.ts:128-145`), so the suite is green while the real list/detail cannot load.
2. **Status vocabulary mismatch.** Indexer stores `PENDING|APPROVED|REJECTED|REVOKED` (`index.ts:350`); detail gates verification on `engagementStatus !== "Resolved"` (`engagement-detail.tsx:~162`), a value never produced, so the form stays enabled after resolution. Fixture uses `"Pending"` (`fixtures.ts:133`).
3. **No chain-vs-indexer signalling in the engagements slice.** Readiness exists only for Valuable Actions (`apps/web/hooks/useValuableActionReadiness.ts`, `components/valuable-actions/valuable-action-readiness-banner.tsx`; endpoint `index.ts:266-304`, which is derived from `valuable_actions.updatedAt`, not engagement freshness and reports `blockLag: "0"` / chainHead = indexed block). `/engagements` and detail have none. After submit the form only says "It will appear after the indexer updates" (`engagement-submit-form.tsx:~92`).
4. **No chain fallback on detail.** Detail reads only GraphQL; no `useReadContract` against `Engagements.getEngagement` (`contracts/modules/Engagements.sol:470-499`; returns typeId, participant, evidenceCID, status, createdAt, verifyDeadline, jurors, approvals, rejections, resolved).
5. **Lifecycle events not projected.** Handlers exist for Submitted, JurorsAssigned, JurorsSelected (VerifierManager), Verified, Resolved, Revoked (`index.ts:1101-1218`). Missing: `AppealSubmitted` (`Engagements.sol:77`, emitted `:281`), `EngagementResolved` vote tallies, and the SBT mint (`ValuableActionSBT.TokenIssued`, `ValuableActionSBT.sol:24,234`); `ValuableActionSBT` is allow-listed for discovery (`src/discovery/module-key-allowlists.ts:15`) and has an ABI (`apps/indexer/abis/ValuableActionSBT.json`) but is not a contract in `ponder.config.ts:96-112`. No on-chain event reference (tx hash/block) is stored for any engagement transition (`ponder.schema.ts:101-111`), so Manager cannot show "the on-chain event as evidence" (QA 3).
6. **Contract reality limits QA step 3.** `AppealResolved` is declared (`Engagements.sol:78`) but never emitted and there is no appeal-resolution function (`grep` shows only `submitAppeal` at `:262`); `revoke` silently no-ops unless the engagement is resolved+Approved (`:286-299`) and is `restricted` (governance/AccessManager). The detail view has no appeal action nor appeal display; web has no reference to `submitAppeal`/`AppealSubmitted`.
7. **Verify UX gaps.** Juror table key is `${juror}-${decision}` (`engagement-detail.tsx:~140`); success/error for `verify` rely on router.refresh while the indexer lags; `resolveExpired` (`Engagements.sol:247`) has no UI.

What already works (keep): `/engagements` + `/engagements/[engagementId]` routes (`apps/web/app/engagements/**`), submit modal/form with IPFS manifest upload then `Engagements.submit` (`engagement-submit-form.tsx`), juror verify write via `COMMUNITY_MODULE_ABIS.engagements` (`engagement-detail.tsx`), community-scoped governance link, REST endpoints `GET /engagements` and `/engagements/:id` (`index.ts:192-227`, return `{items,nextOffset}` and `{engagement,jurors}`), `useApiQuery` / `useApiBaseUrl` REST client (`apps/web/hooks/useApiQuery.ts`).

## Scope

- Align Manager list/detail queries with the real indexer entities and ids (S1, S2).
- Normalize and display lifecycle status truthfully, including Revoked and juror decisions (S3).
- Engagement-scoped projection readiness + chain read fallback on detail (S4, S5).
- Project appeal submission and SBT issuance, store event evidence (tx hash/block) per transition, show them in detail (S6, S7).
- Post-submit "pending indexer" state (S8).

## Non-goals

- Verifier election/credential flows; Valuable Action admin (SHI-27); marketplace/commerce disputes.
- Shadow persistence for engagement creation (no Manager-side DB or local cache pretending to be a record).
- Any Solidity change (appeal resolution, `AppealResolved` emission, revoke semantics) — surfaced as limitation, see open questions.
- Indexer `defaultCommunityId` re-derivation outside the engagement handlers.

## Specs

- **S1** `/engagements` list loads from the real indexer shape: query `engagementss(where:{communityId}, orderBy:"submittedAt", orderDirection:"desc")` → `items` with `id, engagementId, communityId, valuableActionId, participant, status, evidenceManifestCid, submittedAt, resolvedAt` (`generated/schema.graphql:816-826`). No `claims`/`claimss`/`claimant` remains in the engagements queries. Community filter and pagination (`after`/`limit`) keep working.
- **S2** Detail loads `engagements(id: "<communityId>:<engagementId>")` (String id) plus `jurorAssignmentss(where:{communityId,engagementId})`, ordered by weight desc, mirroring REST `/engagements/:id` (`index.ts:207-227`). Route `/engagements/[engagementId]` accepts the composite id; list links use the composite id. Not-found shows a "not indexed yet" state (see S5), not a generic failure.
- **S3** Status is rendered from the indexer vocabulary `PENDING|APPROVED|REJECTED|REVOKED` via one mapping helper (labels + i18n in `lib/i18n.ts` `engagementList`/`engagementsPage`); verify form is disabled for any status other than `PENDING`; juror table keys are stable (`communityId:engagementId:juror`).
- **S4** Engagement readiness: a `GET /communities/:communityId/engagements/readiness` indexer endpoint returns `{status: healthy|lagging|unavailable, indexedBlock, chainHeadBlock, blockLag, indexedAt, details}` computed from real projection freshness (latest engagement/juror activity vs chain head, not a constant lag of "0"); Manager shows a banner on `/engagements` and detail reusing `mapValuableActionReadiness` semantics (`useValuableActionReadiness.ts:~30-60`). QA 4: indexer lagging ⇒ banner `lagging`.
- **S5** Detail chain fallback: when the projection row is missing or readiness is `lagging`/`unavailable`, detail reads `Engagements.getEngagement(engagementId)` via wagmi and renders chain-sourced status/participant/jurors/approvals/rejections/deadline labelled "Chain (not yet indexed)"; when both agree it labels "Indexed". A mismatch (chain resolved, projection pending) is shown explicitly as "Chain-confirmed, indexer pending". Needs community → Engagements address from `useCommunityModules` (`engagementsManager`, `hooks/useCommunityModules.ts:25`).
- **S6** Projection of lifecycle evidence: new columns on `engagements` (`approvalsCount`, `rejectionsCount` from `EngagementResolved`, `lastEventName`, `lastEventTxHash`, `lastEventBlock`) and a new `engagement_appeals` table from `Engagements:AppealSubmitted` (`appealId, communityId, engagementId, appellant, reason, status "PENDING", submittedAt, txHash`). `AppealResolved` is projected if/when emitted (handler tolerant, no assumption). Handlers stay idempotent under replay (same pattern as `onConflictDoUpdate` at `index.ts:1107-1130`) and keep `resolveOrAlert` community scoping. REST `/engagements/:id` returns the new fields; ABI event-compat test updated (`apps/indexer/test/unit/abi-event-compatibility.test.ts`).
- **S7** SBT record: `ValuableActionSBT` added to `ponder.config.ts` and `TokenIssued` projected into an `engagement_sbts` table (`tokenId, kind, communityId, subject, txHash, blockNumber, issuedAt`); detail shows "SBT minted" with token id and tx when an `APPROVED` engagement's participant has a matching token issued in/after the resolution tx. Correlation rule must be stated in code (same tx hash as `EngagementResolved`, since `_resolveEngagement` mints in the same tx, `Engagements.sol:341-367`).
- **S8** Submit UX: after `Engagements.submit` confirms, form shows the tx hash and "Confirmed on-chain, waiting for indexer" until the engagement appears in the projection (poll list/detail, stop on appearance or timeout → "still not indexed; chain read available" linking S5). It validates community/action inputs and replaces `alert(...)` with inline errors. No local persistence of the submitted record.
- **S9** Appeal display (read-only) and appeal action: detail shows appeal(s) with reason and on-chain tx; a participant whose engagement is `REJECTED` and has no pending appeal sees "Submit appeal" calling `Engagements.submitAppeal(engagementId, reason)` (`Engagements.sol:262`). UI states that resolution of appeals is not available on-chain yet (no resolve function) — see Q1.
- **S10** Revoked: detail shows REVOKED with the `EngagementRevoked` revoker/tx evidence (handler at `index.ts:1208` extended to store revoker/tx). UI shows no revoke button (governance-only, `restricted`); links to community-scoped governance (`communityProposalsPath`).
- **S11** Docs: update `.github/project-management/IMPLEMENTATION_STATUS.md` row `3.3 Valuable Action & Engagement` (line ~67) and its SHI-19 mention (line ~35) to reflect what shipped; add the QA section to the PR.

## QA: how to test (Base Sepolia) — from the issue

1. Submit an engagement for an active Valuable Action → appears in `/engagements` with status and evidence; verifiers see it in review.
2. Verifiers approve → engagement resolves, SBT is minted, Manager shows the resolved state and the SBT record.
3. Reject / appeal / revoke paths each show the correct lifecycle state with the on-chain event as evidence.
4. Indexer lagging → readiness banner `lagging`; detail falls back to chain reads where possible.

Mapping: QA1 → S1, S2, S8; QA2 → S3, S6, S7; QA3 → S6, S9, S10 (appeal *resolution* is not producible on-chain, see Q1); QA4 → S4, S5.

## Open questions

- **Q1 (product/contract, non-blocking for T1–T8):** `AppealResolved` is never emitted and no function resolves appeals (`Engagements.sol:78,262-284`). QA step 3 "appeal" can therefore only show appeal *submitted/pending*. Default assumption: ship S9 as submission + pending display and record the contract gap as follow-up (needs a Solidity issue labelled `domain:contracts`). Decide: accept this, or block T9's appeal part on a contract issue.
- **Q2 (scope, affects T8):** Indexing `ValuableActionSBT.TokenIssued` adds a new contract to `ponder.config.ts` and a table. Default: include it (QA2 explicitly requires "the SBT record"). Alternative: read the SBT on-chain from Manager instead (no indexer change) using `ValuableActionSBT` reads; confirm which the maintainers prefer.
- **Q3 (assumption):** composite engagement id `"<communityId>:<engagementId>"` becomes the route param. Default: yes (matches indexer ids and `/engagements/:id`); old numeric-only links will show "not found".
- **Q4 (assumption):** `/engagements` without `communityId` keeps listing across communities; readiness is shown only when a community is selected (readiness is per community).
